i started writing code because i wanted to understand what computers were doing when nobody was watching. that curiosity usually started with breaking things, followed by hours of reading documentation and assembly outputs to understand why they broke.

most of my work lives in systems programming, developer tools, and computer architecture. if a developer tool takes 40 minutes of debugging configuration files before you can write a single line of code, i consider it a personal insult.

developer tooling · bash & cross-platform unix

an environment installer that doesn't blow up your machine.

every time i set up a fresh linux or mac machine, my terminal broke. i would easily burn three to four hours debugging PATH exports, broken package managers, and missing permissions instead of writing actual software.

existing bootstrap scripts either make wild assumptions (like assuming everyone is on standard ubuntu) or greedily overwrite existing dotfiles without asking. i built agent-setup as a single-command orchestrator that inspects what's already installed, stays strictly idempotent, and configures an entire production dev environment in under 40 seconds.

rule: never clobber existing configs, and exit with useful errors instead of silent failures.

computer architecture · interactive simulation

watching modern cpus make wild guesses in real-time.

modern processors don't wait for your code to execute before deciding which branch to take. they make speculative bets on every clock cycle. when they guess right, code is blistering fast. when they guess wrong, the entire execution pipeline is discarded and the CPU stalls.

reading state-transition diagrams in a textbook never quite conveyed the physical cost of a mispredict. so i built an interactive simulator that models 2-bit saturating counters, Branch History Tables (BHT), and Branch Target Buffers (BTB). you can step through branch histories cycle by cycle and visually see where latency penalties accumulate.

lesson: seeing pipeline stalls visually makes hardware trade-offs click in seconds.

quantum algorithms · state vector optimization

quantum pathfinding without melting my laptop fans.

simulating quantum circuits on classical computers is a quick way to turn your laptop into a noisy space heater. state vectors scale exponentially: each additional qubit doubles the memory footprint.

while researching emergency evacuation optimization using quantum search heuristics, most of my time didn't go into writing equations—it went into pruning state spaces, bounding matrix dimensions, and keeping memory low enough that standard hardware wouldn't crash midway through evaluation.

takeaway: theoretical quantum elegance means nothing if classical simulation chokes on memory.
